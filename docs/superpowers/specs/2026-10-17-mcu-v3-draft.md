# BonettoR32V MCU (contract v3): DRAFT for the user's review

Status: **draft**. Nothing here is built or decided until the user approves it. Decisions marked
**[Decide]** are the user's. Each one lists the lead's recommendation first. Area figures are the
lead's **projections** (sky130_fd_sc_hd with the H004 synthesis config, about 20 µm² per
flip-flop). None of them is measured yet.

## 1. Intent

Turn the area-minimal RV32E core into a small but genuinely useful microcontroller that fits ONE
Tiny Tapeout 1x1 tile. "Useful" is measured against an Arduino Uno: blink and dim LEDs, read
buttons, talk over serial, run a timer, drive a servo or buzzer, and act as an **IR remote**
(transmit and receive). It should boot and run standalone from a flash chip, and accept new
programs over serial like an Arduino.

- **Goal:** Arduino-class *peripherals and usability* in one 1x1 tile.
- **Non-goal:** Arduino-class *speed*. The core trades speed for area (section 9).
- **Anti-goal:** a peripheral set so big the core has to grow back on-die registers, or the
  design misses 1x1.

## 2. Budget

| Item | Area (µm²) |
|---|---|
| 1x1 cap, stock TT flow, timing-repair buffers included (measured, Task 8) | ~13,900 |
| Core today: H002 V2 (registers + pc in RAM) / H005 in progress | 5,186 / ~4,900 (measured on branches) |
| Room for peripherals and the bus, keeping ~1,000 margin for repair buffers | **~8,000** |

## 3. Core changes (small)

- **Peripheral bus.** IO space stays at `addr[31] = 1`. Registers decode from `addr[6:2]` (32
  word slots), and everything else aliases. Byte and word accesses both work: a register's bits
  sit in the low byte(s).
- **Interrupts** (section 6). **[Decide]** whether exceptions stay fatal.
- **WFI** stops all SPI traffic until an interrupt is pending. That's the low-power idle.
- **Unchanged:** RV32E, spec-minimum decode, the core region for registers, the pc and the IR.

## 4. Memory board and pins

TT gives 8 inputs (`ui`), 8 outputs (`uo`) and 8 bidirectional pins (`uio`). The memory board
decides how many `uio` pins stay free. The user asked for something that works entirely on the
TT demo board, with no PMOD and no breadboard, so option C now comes first.

**C (recommended; the user's direction is to stay on the board): the demo board's management MCU
emulates the memory.** Target board: the **TT ETR demoboard** (https://tinytapeout.com/specs/pcb-etr/).
Its management chip is an **RP2350B** (520 KB SRAM), "connected not only to the project MUX but to
all the ASIC I/O as well as the clock and reset pins"
(https://tinytapeout.com/guides/get-started-demoboard-etr/). In RP-control mode it drives
`ui_in`, drives or reads each `uio` pin per `uio_oe_pico`, reads `uo_out`, generates the project
clock and can hold reset. The bullets below say RP2040 (the older board), but they apply equally
to the RP2350B, which is the stronger chip. Still to verify: the RP2350B GPIO number for each
`uio` pin (schematic), and the SCK rate a PIO SPI-slave emulator sustains.
- The TT PCB spec (https://www.tinytapeout.com/specs/pcb) says the demo board's RP2040 drives the
  project inputs and bidirectional pins and reads the bidirectional pins and outputs. It also
  supplies the project clock.
- The RP2040 firmware therefore serves our exact 23LC512 protocol on uio[0..3] from its own SRAM
  (264 KB), using a PIO SPI-slave program. NanoV was reportedly tested this way; the lead must
  verify that.
- What this replaces:
  - **Flash boot:** the RP2040 loads the program from its own flash (or from USB) into the
    emulated RAM before releasing reset. No BOOT mode and no flash chip select are needed on the
    die, saving about 250 µm².
  - **Arduino-style upload:** copy the program over USB to the RP2040.
  - **Serial monitor:** the RP2040 bridges UART TX (`uo[0]`) and RX (`ui[0]`) to USB CDC.
- uio[4..7] are all free for bidirectional GPIO and I2C.
- **Limits:**
  - **Speed.** A PIO SPI slave has to answer the first data bit within half an SCK period after
    the last address bit. The achievable SCK, and so the clock, must be **measured**. It may cap
    the clock below the 40 MHz goal. The RP2040 can be overclocked, and the core sets SCK, with
    no maximum phase length.
  - **The demo board's own parts.** The DIP switches share `ui`, and the 7-segment display
    shows `uo`. The firmware must leave the switches undriven, or document their positions.
  - **IR parts.** An IR LED and a TSOP receiver aren't on the board. For the IR remote, those
    2-3 parts plug into the PMOD header sockets.
- **Gates:** unchanged. The RP2040 implements the contract's 23LC512 semantics, and the RP2040
  firmware becomes a project deliverable with its own tests.

**A: the current 23LC512 SPI RAM plus a SPI flash on a 5th chip select**, on a custom PMOD or a
breadboard. Single-bit SPI, as today.

| Pin | Function |
|---|---|
| uio[0] | RAM CS_n |
| uio[1] | MOSI |
| uio[2] | MISO |
| uio[3] | SCK |
| uio[4] | FLASH CS_n |
| uio[5] | GPIO / SPI-device CS_n (alt) |
| uio[6] | GPIO / I2C SDA (alt, open drain) |
| uio[7] | GPIO / I2C SCL (alt, open drain) |
| uo[0] | GPIO / UART TX (alt) |
| uo[1] | GPIO / PWM0, IR carrier (alt) |
| uo[2] | GPIO / PWM1 (alt) |
| uo[3] | GPIO / PWM2 (alt) |
| uo[4] | GPIO / timer compare out (alt) |
| uo[7:5] | GPIO |

**B: Tiny Tapeout's standard QSPI PMOD** (flash plus two 8 MB PSRAMs), the TinyQV pinout. The
lead must verify the details below before relying on them.

| Pin | Function |
|---|---|
| uio[0] | flash CS |
| uio[1], uio[2], uio[4], uio[5] | SD0-SD3 |
| uio[3] | SCK |
| uio[6], uio[7] | RAM CS |

- **Pros:** an off-the-shelf board. Quad mode would roughly triple or quadruple memory
  bandwidth, which is the biggest speed lever available (section 9).
- **Cons:**
  - It uses all 8 `uio` pins, so there are no bidirectional GPIO and no I2C.
  - PSRAM limits CS-low time to about 8 µs (tCEM), which constrains slow bit-serial
    transactions.
  - Pages wrap at 1 KB.
  - Moving to quad SPI is a core change.

## 5. Peripherals

All registers are 32-bit slots at `0x8000_0000 + 4*n`. The table gives the lead's proposed map.

| Slot | Name | Bits | Function |
|---|---|---|---|
| 0 | GPIO_OUT | 8 | `uo_out` (as today) |
| 1 | GPIO_IN | 8 | `ui_in` (as today) |
| 2 | UIO_OUT / UIO_DIR / UIO_IN | 3 + 3 + 3 | uio[7:5] as GPIO |
| 3 | ALTFN | 8 | per-pin alternate-function enables (UART TX, PWM0-2, compare out, I2C) |
| 4 | TIMER_CNT | 16 | free-running counter; a write sets it |
| 5 | TIMER_CTRL | 8 | prescaler (2^0..2^15, 4 bits), compare-out mode (toggle / PWM / off), capture edge (rise / fall / both), enables |
| 6 | TIMER_CMP | 16 | compare value. A match sets IRQ_CMP; optionally auto-reload sets CNT to 0 |
| 7 | TIMER_CAP | 16 | count latched on the selected `ui[1]` edge; sets IRQ_CAP |
| 8 | PWM_PER | 10 | shared PWM period, in clocks; 20 MHz / 526 = 38 kHz |
| 9-11 | PWM_DUTY0-2 | 10 each | duty per channel. PWM0 can be ANDed with the timer compare output to make a gated IR carrier |
| 12 | UART_DATA | 8 | a write sends a byte (1-byte TX buffer); a read takes the received byte (1-byte RX buffer) |
| 13 | UART_CTRL | 16 | baud divisor (13 bits), flags: TX busy, RX full, RX overrun |
| 14 | SPI_DATA | 8 | software SPI byte transfer on the shared bus with a chosen CS: flash programming, SD card, displays |
| 15 | SPI_CTRL | 4 | CS select (flash, uio[5] device), busy |
| 16 | I2C | 8 + 4 | **[Decide]**: a hardware I2C master (~1.0k), or software through uio[6:7] open drain (~0) |
| 17 | IRQ_EN | 8 | timer compare, capture, UART RX, UART TX empty, GPIO edge, delta-sigma |
| 18 | IRQ_PEND | 8 | pending flags; write 1 to clear |
| 19 | GPIO_EDGE | 8 + 8 | per-`ui`-pin edge-interrupt enable and polarity |
| 20 | DSADC | 12 | delta-sigma result. External RC: `uo[5]` drives the feedback and `ui[2]` reads the comparator. A counter over a 2^N window gives about 8-10 bits at slow rates (optional) |
| 21 | BOOT | 1 | fetch source: flash (set at reset) or RAM (section 7) |

**Projected area:**

| Block | Area (µm²) |
|---|---|
| Timer (counter, prescaler, compare, capture, output) | 1,400 |
| 3 PWM channels with a shared period counter | 1,000 |
| UART TX + RX | 1,300 |
| SPI byte shifter (shares the core's SPI pins) | 400 |
| GPIO (uio direction, ALTFN, edge interrupts) | 700 |
| Interrupt controller + CSR logic (section 6) | 800 |
| Boot mode and flash CS (section 7) | 250 |
| Bus decode / read mux | 600 |
| **Subtotal** | **~6,450** |
| Optional: delta-sigma ADC | 400 |
| Optional: hardware I2C master | 1,000 |

The subtotal fits the ~8,000 budget. The optional pair would bring it to ~7,850, which is tight.

## 6. Interrupts

- **Recommended:** a minimal standard machine-mode interrupt. Standard toolchains and C
  handlers then just work.
  - CSRs: `mstatus` (MIE and MPIE only), `mie` (MEIE), `mip` (MEIP), `mtvec` (direct mode),
    `mepc`, `mcause`.
  - Only CSRRW, CSRRS and CSRRC (plus the immediate forms) on those CSRs, and MRET. Other CSR
    numbers read 0 and ignore writes.
  - `mepc`, `mtvec` and `mcause` live in the core region, the same trick as the pc and SERV's
    "CSRs as register-file entries". Only MIE and MPIE sit on the die.
  - One interrupt line: the OR of the enabled IRQ_PEND bits. Software reads IRQ_PEND for the
    source.
  - Worst-case latency is about two instructions (~75 µs at 20 MHz), which is fine for IR,
    UART at 9600 baud and buttons.
- **Exceptions: they trap to `mtvec`** (the user's decision, 2026-10-17).
  - These take the standard machine-mode trap, with `mcause` set:
    - ECALL (11) and EBREAK (3);
    - misaligned JAL, JALR and branch targets (0);
    - the 0x00000000 and 0xFFFFFFFF words (illegal instruction, 2).
  - On a trap, `mepc` gets the trapping pc, `mstatus.MPIE` gets MIE, MIE goes to 0, and execution
    jumps to `mtvec`.
  - Reserved encodings stay UNSPECIFIED. A core may trap them as illegal or execute them, but
    must stay live.
  - The contract's "fatal halt" rule goes away. The gates change accordingly: the ISS trap
    model, the trap programs (which test handlers and MRET), and riscv-formal's trap and pc
    checks. The cosim harness and the liveness fuzz then detect the end of a program from a
    handler convention, for example the handler writing a magic value to GPIO.
  - Projected extra cost on top of interrupts: about 200-400 µm² (the cause codes plus the
    trap-entry sequence).
- **Gates:** riscv-formal supports interrupts (rvfi_intr). The ISS gains a CSR and interrupt
  model, and cosim gains interrupt programs: a timer tick, UART RX, a GPIO edge.

## 7. Standalone boot and Arduino-style upload

- **Reset.** BOOT = flash: fetches and loads read the **flash** (0x03 READ, 24-bit address),
  while stores and core-region traffic go to the **RAM**. A tiny loader at the start of flash
  copies the program from flash to RAM (`lw` from flash, `sw` to RAM), then writes BOOT = RAM.
  From then on everything runs from RAM, exactly as today.
  - Cost: one mode bit, a second CS and 8 address bits. No boot ROM.
  - Projected time at 20 MHz: about 0.3 s per 16 KB copied. That's a projection, not a
    measurement.
- **Upload,** like Arduino's bootloader. The same loader first waits about 0.5 s for a sync byte
  on the UART. If it arrives, it receives a program and writes it to flash with SPI_DATA (write
  enable, page program, erase). A host script (Python) plays the role of avrdude.
- **EEPROM equivalent:** a reserved flash sector, through the same SPI_DATA path.

## 8. The IR remote, end to end

- **Transmit (NEC):**
  1. PWM0 runs the 38 kHz carrier at 1/3 duty.
  2. The timer compare output gates it (AND) on `uo[1]`, which drives the IR LED through a
     transistor.
  3. Software loads the next mark or space duration into TIMER_CMP on each compare interrupt.
     The 562 µs units are about 15 instructions apart, plenty.
- **Receive:**
  1. A TSOP38238 demodulator output goes to `ui[1]`.
  2. The capture interrupt fires on both edges. Software computes widths from TIMER_CAP
     differences and decodes NEC (9 ms leader, 562 µs units).
- **Learning remote:** store the raw edge timings in RAM, then replay them through the TX path.

## 9. Gap to an Arduino Uno (ATmega328P at 16 MHz)

| Uno | This MCU (draft) | Gap |
|---|---|---|
| ~16 MIPS (AVR, about 1 instruction per clock) | ~0.027 MIPS at 20 MHz (V2: ~741 clocks per instruction). 40 MHz is the max with the 23LC512 (20 MHz SCK) | **About 600x slower.** Libraries that bit-bang microsecond timing (NeoPixel, software serial, `delayMicroseconds` precision) won't work. Everything timing-critical must be hardware |
| 32 KB flash, 2 KB SRAM, 1 KB EEPROM | 16 MB+ flash (chip-dependent), 64 KB RAM, a flash sector as EEPROM | **Better** |
| 20 GPIO, all bidirectional, with pull-ups | 8 in, 8 out, 3 bidirectional (option A) | Fewer bidirectional pins: TT pad types are fixed. No internal pull-ups |
| 6 PWM, 3 timers, input capture | 3 PWM, 1 timer with compare and capture | Fewer channels. More cost ~300 µm² each |
| 10-bit ADC, 6 channels, analog comparator | optional 1-channel delta-sigma with an external RC, slow | **No real analog.** TT analog needs analog tiles |
| UART, SPI, I2C hardware | UART and SPI hardware; I2C hardware or software | Close |
| External and pin-change interrupts on every pin | edge interrupts on the 8 `ui` pins | Close |
| Hardware multiply (2 cycles) | none: RV32E without M, software multiply (hundreds of instructions) | Slow math. **[Decide]:** a serial Zmmul multiply instruction (~700-1,000 µm², reusing the serial ALU, ~32 extra cycles per multiply) |
| Watchdog, sleep, brown-out | timer-based watchdog (software), WFI sleep, no brown-out | Close (no brown-out) |
| USB upload and the Arduino IDE core | UART upload loader, GCC RV32E, no Arduino core yet | **Software work:** an Arduino core port (`pinMode`, `digitalWrite`, `analogWrite`, `millis`, `Serial`, `tone`, `attachInterrupt`, `SPI`, `Wire`) plus an upload tool |

**Closing the speed gap costs area or pins:**
- Quad SPI (option B): about 3-4x.
- A 40 MHz clock: 2x, and free if timing closes.
- Caching hot registers on the die: area.

Even all three together leave the MCU about 50-100x slower than a Uno. The honest pitch is an
*Arduino-like, very small, very slow* MCU: it's ideal for IR, buttons, LEDs, serial and sensors,
and wrong for bit-banged high-speed protocols.

## 10. Verification plan (the gates move with the contract)

- **ISS:** peripheral models (timer, PWM, UART, SPI shifter, GPIO edges, IRQ, CSRs, boot mode).
  The cosim harness gains pin-level models: a UART terminal, an IR LED and receiver loopback,
  and a flash chip.
- **New cosim programs:**
  - IR NEC loopback (TX into RX);
  - UART echo;
  - a timer interrupt tick;
  - PWM duty measured at the pins;
  - flash boot plus copy;
  - upload over UART into flash;
  - GPIO edge interrupts;
  - the liveness fuzz with peripherals enabled.
- **Formal:** register read/write checks per peripheral, interrupt entry and MRET, and the
  existing core checks with interrupts (rvfi_intr).
- **Gate level:** the TT test runs the IR loopback and UART echo on the netlist.

## 11. Phasing

1. Finish the core: V2 through the v2 formal gate, then H005 and later diets.
2. The user approves this spec, and the lead writes contract v3 plus the plan.
3. Gates first (ISS, harness models, programs, formal checks).
4. A peripheral seed: simple, correct, not optimized.
5. Area loop on the peripherals, one hypothesis track per block, measured against the 1x1
   budget.
6. Champion round: harden 1x1, tilefit, TT CI. Then the Arduino-style core and the upload tool
   (software).

## 12. Decisions

Decided by the user on 2026-10-17:
- **Memory board: TT's official QSPI Pmod**, option B: W25Q128 flash plus 2x 8 MB PSRAM on
  uio[0..7]. This supersedes the option C recommendation.
  - The contract and gates move to 24-bit addresses.
  - PSRAM's CS-low limit (about 8 µs, tCEM) must be met by every transaction.
  - Code boots from flash (XIP, or copied to PSRAM).
  - Single SPI first; quad mode later as a speed hypothesis.
  - All `uio` pins are used. GPIO is the 8 `ui` and 8 `uo` lines, plus an optional SPI I/O
    expander (MCP23S17) on uo/ui for bidirectional GPIO. The board's exact pinout and memory
    parts must be verified from its schematic first.
- **Radio:** off-chip, with no on-chip RF (TT digital tiles; analog muxes far too slow for
  RF). Either a BLE module over the UART or a LoRa module (SX1262/RFM95) over SPI on uo/ui.
- **Pins:** TT gives 24 user I/O on every shuttle (GF180 included), so expanders are the GPIO
  path.
- **Exceptions:** trap to `mtvec` (section 6).
- **Multiply:** none. Software multiply; no M or Zmmul.
- **Clock:** a 40 MHz target if timing closes, with a 25 ns signoff period. Under option C the
  memory emulation may cap it; measure.

Still open (recommendation first):

1. **I2C:** software through uio[6:7], or a hardware master (+~1.0k).
2. **Delta-sigma ADC:** include it (+~0.4k), or leave it out.
